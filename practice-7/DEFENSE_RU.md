# Защита Task 7: Полка PWA

## Короткое выступление
«Я расширил существующее React-приложение до Progressive Web App. Работа находится в отдельной папке practice-7 и собирается Vite. Старые страницы, CRUD, фильтры, dashboard, внешний каталог и архитектура сохранены. Manifest отвечает за установку и внешний вид отдельного приложения. Service worker отвечает за перехват запросов и работу без сети. Он кэширует готовые JS/CSS-файлы, включая lazy chunks, а публичный API использует network-first с ограниченным кэшем. При отсутствии соединения уже загруженные данные доступны, а интерфейс явно предупреждает, что это сохранённая копия. Обновление активируется по нажатию пользователя, после чего старые версии кэша удаляются».

## Порядок демонстрации, 4–5 минут
1. Показать папку practice-7 и структуру common/features. Запустить опубликованную страницу.
2. CRUD локальной полки → фильтры → dashboard. Это показывает сохранение предыдущих функций.
3. DevTools Application → Manifest: имя, standalone, start_url/scope, два размера иконок. Показать установку, если браузер её предлагает.
4. Онлайн найти Tolkien и открыть одну книгу. Затем Offline, перезагрузить, открыть тот же запрос/книгу. Показать уведомление о сохранённой копии.
5. Новый запрос без кэша: показать понятную ошибку, а не обещать доступ ко всему интернету.
6. /#/offline → Retry: отсутствие сети; затем Online → Retry, успешное восстановление.
7. 320px portrait и landscape: навигация, форма, карточка, dashboard.
8. Показать Cache Storage и код allowlist. Объяснить цикл обновления по кнопке.

## Вопросы и ответы
**Что делает PWA приложением?** HTTPS, manifest, installable metadata/icons и service worker, который обеспечивает офлайн-возможности. Установка зависит также от браузера.

**Чем SW отличается от React?** Это отдельный событийный worker вне DOM. React рисует UI, SW обрабатывает install/activate/fetch и может отвечать из Cache Storage.

**Почему нельзя кэшировать всё?** Авторизация, токены и приватные ответы могут попасть не тому пользователю или устареть. Здесь кэшируются только два явно перечисленных публичных пути Open Library.

**Cache-first против network-first?** Статика меняется редко, поэтому сначала кэш. Публичные данные могут обновляться: сначала сеть, только при сбое/таймауте сохранённая копия. Это не означает, что свежесть гарантирована offline.

**Как обновляется версия?** Сборщик считает hash всех production-файлов и шаблона worker. Новый SW получает другое содержимое, устанавливает новый кэш и ждёт. UI предлагает обновление. По кнопке skipWaiting, затем activate, очистка старых кэшей своего префикса и reload.

**Почему не skipWaiting сразу?** Старая вкладка может использовать несовместимые файлы или иметь несохранённую форму. Пользователь получает контроль над моментом перезагрузки.

**Как ограничивается объём?** Для публичного API максимум 50 записей, для runtime-статики 60, срок хранения 24 часа. Shell хранится целиком для одной актуальной версии.

**Почему navigator.onLine недостаточно?** Устройство может быть в Wi-Fi без доступа в интернет. Поэтому есть реальный GET без кэша, обработка ошибок fetch и таймаут.

**Зачем HashRouter?** GitHub Pages не имеет серверного SPA-rewrite. Hash не отправляется серверу, поэтому /#/books/id открывает тот же index.html без 404 при refresh.

**Где хранятся книги?** Локальная полка наследует fake API/localStorage; публичный каталог берётся из Open Library. SW не превращает локальную полку в облачную БД и не синхронизирует её между устройствами.

**Как соблюдается архитектура?** common не зависит от features; features не импортируют друг друга; API/services отделены от компонентов. Общая PWA-логика находится в common/pwa, композиция — App/RootLayout. Проверка границ запускается вместе с lint.

**Работает ли Firebase?** Код интеграции и тесты сохранены, но реальные вход/Google OAuth без конфигурации проекта не подтверждены. Это нужно честно сказать, а не демонстрировать фиктивную авторизацию.

## Разница тестов
Unit tests проверяют алгоритмы и обработку ошибок. jsdom проверяет React-взаимодействие, но не настоящий service worker или install prompt. Build подтверждает компиляцию. Проверка браузером нужна отдельно для offline lifecycle, установки, обновлений и mobile layout.
